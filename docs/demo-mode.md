# Demo / Simulation Mode

## What DEMO_MODE is for

`DEMO_MODE` lets the complete firmware pipeline — acquisition, analytics, status
classification, logging and reporting — run on a **bare ESP32 with nothing wired
to it**. You can flash a board straight out of the bag and watch a realistic
cold-chain monitor operate.

## What it is not

> **Simulated output is not evidence that any sensor works.**
>
> In demo mode the firmware does not read, probe, or in any way touch the DHT11,
> the MPU6050, the NEO-6M or the SD card. The numbers are generated by
> [`src/demo/DemoSensorData.cpp`](../src/demo/DemoSensorData.cpp). A demo
> transcript demonstrates that the *software* works. It says nothing about
> hardware.

The firmware is built so this cannot be blurred by accident. Every simulated
value is tagged `DataSource::SIMULATED`, every serial block prints its own
provenance tag, and the storage layer reports `SIMULATED` rather than `LOGGING`
so that even a screenshot discloses what it is:

```
ENVIRONMENT   [DEMO/SIMULATED]
  Temperature : 28.0 C

STORAGE
  Status  : SIMULATED
```

## Switching modes

Mode is a compile-time choice. Two PlatformIO environments are pre-defined:

```bash
pio run -e esp32dev-demo -t upload    # DEMO_MODE=1  (default)
pio run -e esp32dev-real -t upload    # DEMO_MODE=0  (real drivers)
```

Or set it directly in [`config.h`](../src/config.h) when building without
PlatformIO:

```c
#define DEMO_MODE 1
```

### The third option: a mixed build

`DEMO_TRY_REAL_DHT` builds a firmware that reads the **real DHT11** while
simulating motion and GPS:

```c
#define DEMO_MODE          1
#define DEMO_TRY_REAL_DHT  1
```

This is genuinely useful — the DHT11 is the cheapest sensor to wire, so you can
validate the real acquisition path with one component attached. Records from this
build are honest field by field:

```
ENVIRONMENT   [REAL SENSOR]        <- actually measured
MOTION        [DEMO/SIMULATED]     <- synthesised
LOCATION      [DEMO/SIMULATED]     <- synthesised
```

This is exactly why `SensorData` carries per-field provenance instead of one
global `demoMode` flag.

## Exactly what is simulated

| Subsystem | In `DEMO_MODE=1` | Provenance tag |
|---|---|---|
| Temperature / humidity | Simulated, or real if `DEMO_TRY_REAL_DHT=1` | `SIMULATED` / `REAL_SENSOR` |
| Accelerometer / gyroscope | Simulated | `SIMULATED` |
| GPS position | Simulated | `SIMULATED` |
| MicroSD | **Not touched.** Row formatted, counter advanced, nothing written | `StorageStatus::SIMULATED` |
| Trend analytics | **Real code**, running on simulated input | — |
| Status engine | **Real code**, running on simulated input | — |
| Serial reporting | **Real code** | — |

The analytics and status engine are never simulated. They are the same objects
the real build uses, executing the same rules — only their input differs. That is
the point of the interface seam described in
[`architecture.md`](architecture.md).

## Simulated value ranges

| Signal | Range | Behaviour |
|---|---|---|
| Temperature | 28.0 – 35.0 °C | 7-min thermal cycle + small noise |
| Humidity | 45 – 70 % RH | Inversely coupled to temperature |
| Acceleration X, Y | ±0.18 m/s² | Noise about zero |
| Acceleration Z | 9.81 ±0.10 m/s² | Gravity, package lying flat |
| Gyroscope X, Y, Z | ±0.03 rad/s | Noise about zero |
| Shock bump (rough handling) | 3.5 – 6.0 m/s² | ~1 sample in 12 |
| Shock bump (impact) | 9.0 – 14.0 m/s² | ~1 sample in 60 |
| Latitude | 12.9716 ±0.0025 | Heading-based walk |
| Longitude | 80.0434 ±0.0025 | Heading-based walk |
| Altitude | 18.0 ±1.2 m | Noise (Kundrathur is ~15–20 m AMSL) |
| Satellites | 6 – 10 | ±1 per sample |

All values are in `namespace demo` at the top of
[`DemoSensorData.h`](../src/demo/DemoSensorData.h).

## How the values are generated

This is the part that separates a prototype from a random-number generator.

### Not this

```cpp
temperature = random(28, 35);        // 28.4 -> 34.9 -> 29.1 -> 33.8
```

Independent draws jump across the whole range every sample. No physical quantity
behaves that way, and the trend analytics would be meaningless.

### Temperature: a slow cycle plus fast texture

Two components are summed:

**(a) A slow thermal cycle.** A 7-minute sinusoid, centred at 31.2 °C with a
±3.5 °C swing. This is the *signal* — it gives the demo a real story arc: the
cargo warms, crosses the warning bound, peaks near critical, then recovers.

Real cold-chain excursions are slow directional ramps — a compressor duty cycle,
a door left open, ice melting — not white noise. A random walk would both
misrepresent the physics *and* hover near the middle of its band, never
approaching a threshold, so the status engine would never be seen to change
state.

**Why 7 minutes and not 3.** The period is set from the ramp rate it implies. For
a sinusoid the steepest slope is `2π × swing / period`; at 7 minutes that is about
**3.1 °C/min**, plausible for a small insulated box losing cooling. A 3-minute
cycle — tempting, because the arc completes sooner — implies 6.7 °C/min, which is
not plausible for cargo with any thermal mass, and it holds the predictive trend
rule permanently above its threshold so that rule stops distinguishing anything.

> **Consequence worth knowing before you watch:** one full arc takes 7 minutes.
> A 30-second glance will usually show a steady `NORMAL`. That is the system
> working, not the demo being broken. Let it run a few minutes to see the
> `WARNING` and `CRITICAL` transitions.

**(b) Fast sensor texture.** A small bounded random walk (±0.18 °C) added on top,
carried between samples rather than redrawn independently — which is what makes
consecutive readings look *related*, the way a real sensor's do. The result is
rounded to 1 dp to match what a DHT11 actually resolves:

```
30.7 -> 30.6 -> 30.4 -> 30.3 -> 30.0 -> 29.8 -> 29.6 -> 29.5
```

### Humidity: coupled to temperature, not independent

Relative humidity falls as air warms, because warmer air holds more moisture
before saturating. So humidity is derived from temperature at −2.2 %RH per °C,
plus its own small noise — rather than walked independently.

This is both more realistic and more useful: the humidity trace *corroborates*
the temperature story instead of contradicting it. In the captured run,
temperature falling 30.7 → 29.5 °C takes humidity 56.7 → 60.9 %.

### Motion: gravity, noise, and occasional bumps

The baseline is a package lying flat and still: ~9.81 m/s² on Z, noise on X and
Y, matching the few-hundredths-of-a-g noise floor a real MPU6050 shows on a desk.

Transport bumps are injected in **two tiers**, because a real shipment sees two
different things:

- **Rough handling** (a pothole, a shove) — common, crosses `SHOCK_WARNING_MS2`
- **An impact** (dropped, struck) — rare, crosses `SHOCK_CRITICAL_MS2`

Each bump hits one axis and adds a matching rotation, the way a real jolt does: a
package that gets knocked also turns. The sign is random, so a jolt can push the
reading below 1 g as well as above it.

Without these the demo would sit at one status forever and never show the shock
detector or the alarm paths working. The first few samples are left clean so the
demo opens on a settled baseline rather than an immediate alarm.

### GPS: a walk along a heading

The track is generated by turning a heading slowly and stepping along it, rather
than jittering latitude and longitude independently. Independent jitter produces a
cloud of unrelated points; walking a heading produces something that looks like a
vehicle following a road.

Two details that matter:

- **Longitude is scaled by `1/cos(latitude)`.** Longitude degrees are shorter than
  latitude degrees away from the equator. Without this correction the simulated
  track would appear to move faster east–west than north–south.
- **The track is leashed.** If it strays more than ~250 m from the origin the
  heading reverses, so a long demo stays recognisably *at CIT* instead of
  wandering into the next district.

Origin: **12.9716, 80.0434** — Chennai Institute of Technology, Kundrathur,
Chennai, Tamil Nadu.

Satellite count wobbles by at most ±1 per sample, as it does in reality when a
satellite rises or sets — not 6 → 10 → 6.

### Storage: counted, not written

`StorageManager` constructed with `simulate = true` never calls `SPI.begin()` or
`SD.begin()`. The row is formatted exactly as it would be written — same columns,
same precision — the record counter advances, and the bytes go nowhere. In demo
mode each formatted row is echoed to serial prefixed `[csv]`, so the storage
format is visible without a card:

```
[csv] 50,30.7,56.7,0.105,0.098,9.795,0.019,-0.003,-0.012,12.971221,80.043305,17.2,6,NORMAL,1
```

### Randomness is seeded per boot

`demo::seedOnce()` seeds from the ESP32 hardware RNG mixed with the boot-time
microsecond counter, and the thermal cycle starts at a random phase. Two boards,
or two runs of the same board, do not replay an identical trace.

## About the thresholds

> **The thresholds in `config.h` are prototype values. They are not medically or
> industrially certified, are not derived from any pharmaceutical, food-safety,
> WHO or industrial cold-chain specification, and must not be used for real
> perishable or medical cargo.**

A genuine vaccine cold chain is **2–8 °C**. This prototype is demonstrated on a
desk at ambient Chennai temperature, and the simulator walks 28–35 °C
accordingly. Applying a real 2–8 °C band to that input would report `CRITICAL` on
every single sample — which demonstrates nothing, because a status engine that
never changes state cannot be seen to work.

So the upper bounds are placed *inside* the simulated band:

| Threshold | Value | Reachable in demo? |
|---|---|---|
| `TEMP_CRITICAL_LOW_C` | 4.0 °C | No — by design |
| `TEMP_WARNING_LOW_C` | 8.0 °C | No — by design |
| `TEMP_WARNING_HIGH_C` | 33.0 °C | Yes |
| `TEMP_CRITICAL_HIGH_C` | 34.5 °C | Yes, briefly at the peak |
| `HUMIDITY_WARNING_LOW_PCT` | 35 % | No |
| `HUMIDITY_WARNING_HIGH_PCT` | 68 % | Occasionally |
| `HUMIDITY_CRITICAL_HIGH_PCT` | 85 % | No |

The lower bounds are kept at plausible chilled-cargo values and are unreachable
in demo mode; they exist to show the two-sided logic. **Swapping these four
numbers for the real ones is the entire change needed** to point this at actual
chilled cargo — which is the property the threshold design was chosen for.

## What a demo run actually produces

Measured over 400 samples (~13 minutes, about two full thermal cycles):

| Status | Share | Triggered by |
|---|---|---|
| `NORMAL` | ~53 % | — |
| `WARNING` | ~36 % | temperature above warning high; predictive trend; rough handling; tilt |
| `CRITICAL` | ~11 % | temperature above critical high; impact events |

Every rule in the status engine fires at least once in a run of this length,
which is what the simulation was tuned for. The `CRITICAL` share is high compared
with a real shipment because the simulator **deliberately** drives a full
excursion arc twice — the point is to make every state visible, not to model a
typical journey.

## Verifying the logic without hardware

The demo build is itself the test: it exercises the real analytics, status engine,
storage formatter and reporter against controlled input. Useful checks:

| Check | Expected |
|---|---|
| `accel_z` at rest | ~9.7 – 9.9, **not** ~0 |
| Consecutive temperatures | differ by tenths, never jump 3 °C |
| Humidity vs temperature | move in **opposite** directions |
| Latitude / longitude | creep smoothly; stay near 12.9716, 80.0434 |
| Satellites | change by at most ±1 per sample |
| Status over ~7 min | visits `NORMAL`, `WARNING`, and `CRITICAL` |
| Every serial block | carries a `[...]` provenance tag |
| Storage line | says `SIMULATED`, never `LOGGING` |

## Moving to real hardware

1. Wire the modules per [`pinout.md`](pinout.md) — check the GPS TX/RX crossover.
2. Format the MicroSD card as **FAT32**.
3. Build with `pio run -e esp32dev-real -t upload`.
4. Read the boot banner. Each subsystem reports `OK` or `FAILED` individually.
5. Expect no GPS fix indoors — that is normal, and the banner says so.
6. Replace the thresholds in `config.h` with the ones your cargo actually
   requires.

A subsystem that fails to initialise does **not** stop the system. Its fields are
reported `UNAVAILABLE` rather than being filled with fabricated data:

```
ENVIRONMENT   [UNAVAILABLE]
  Temperature : --   (sensor not responding)
```

That is the same principle as everything else here: the firmware would rather
report nothing than report something it cannot substantiate.
